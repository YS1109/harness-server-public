# QQ / Pi 调度与执行记录设计

状态：低频任务/尝试/检查点与调度上下文已实现；QQ/Pi适配、租约和自动调度尚未实现。实际API与接入约定见 [Pi执行记录接入指南](PI-EXECUTION-INTEGRATION.md)。本页保留完整设计和后续边界。

## 场景与目标

远程 Pi 主 Agent 接收 QQ 机器人消息，拆分并下发多个任务。主 Agent 上下文清空、进程重启或执行 Agent 中断后，需要恢复当前用户目标、已下发任务及下一步，避免漏单、重复下发和误报完成。

现有 Session/Workstream 保存交接与长期目标，Idempotency-Key 保护 Harness 写入；基础交接不提供消息去重、执行任务状态机、领取租约或执行中检查点；新增执行记录API提供任务来源去重、条件领取与检查点，仍没有领取租约。execution_group_id 是调用关联信息，不是任务队列或执行保证。

通过新增独立执行记录层覆盖任务快照与检查点。机器人/Pi 负责执行与调度，Harness 提供经过鉴权的记录、条件更新和恢复查询。执行记录不进入长期记忆或 route；任务结束后有稳定知识才另行保存。原有轻量默认和 daily 跳过规则继续有效，不因本设计自动扩大记录范围。

## 三类记录

| 记录 | 最小内容 | 恢复用途 |
| --- | --- | --- |
| 主 Agent 调度上下文 | conversation_id、最新目标/约束摘要、待回答事项、相关 task_id、最近处理的消息标识 | 恢复主 Agent 的调度视图；不保存完整聊天 |
| 执行任务 | task_id、conversation_id、父任务、项目、目标/验收条件、来源去重键、状态、版本、当前 attempt、Session/Workstream 引用 | 查询未完成任务及准确执行状态 |
| 执行尝试与检查点 | attempt_id、执行器/原生会话 ID、已确认完成步骤、当前进度、下一步、代码分支/提交或产物引用、阻塞、结果/验证摘要 | 续接同一任务，区分重试与原执行 |

Task 表示一份稳定工作委托；Attempt 表示一次实际执行。消息、任务、执行尝试、Agent 会话分别使用自己的 ID，不能用 QQ 群 ID 或机器人进程 ID 充当 task_id。多个子任务共享 conversation_id 和 parent_task_id，各自保存检查点；并行任务不覆盖同一个 Workstream 摘要。

消息去重键由可信机器人适配器根据平台、机器人实例、会话与平台消息 ID 生成，建议使用不可逆的命名空间摘要；不保存原始 QQ 账号或整段消息。拆分任务时增加稳定的子任务键。网络重试沿用既有消息到任务的映射，不重新生成 task_id；无平台消息 ID 时，需在本地持久 inbox 生成并保存事件 ID，不能仅按文本去重。

## 保存时机

1. **收到消息、确认接受前**：持久化脱敏需求及来源去重键、task_id 映射。记录失败时不下发；适配器保留本地持久 inbox 或由平台可重放，明确尚未接受。保证不丢消息需要这一入口配合，不能只靠 Agent 提示词。
2. **下发前**：保存执行尝试和待下发记录；下发时携带 task_id/attempt_id。执行器确认后保存原生会话 ID。执行器需能按 attempt_id 去重或查询已启动实例。
3. **重要边界**：阶段完成、产生关键产物、等待用户、准备高影响外部动作、交还主 Agent、上下文压缩或退出前保存简短检查点。由适配器/hooks 自动触发；不用每条消息、每次工具调用或每轮测试都写入。
4. **结果回传**：条件更新任务状态、保存实际验证与结果摘要，并记录待回复事项。用户回复的投递与执行完成分别记状态，不能把“执行成功”当作“QQ 回复已送达”。

主 Agent 恢复时，先读取有界的调度摘要和未完成任务列表，再按需读取待处理任务的最新检查点。默认不读全部 Session、全部事件或历史尝试正文。

## 状态与恢复

执行记录任务状态：`QUEUED → DISPATCHING → RUNNING → SUCCEEDED`，另有 `WAITING_USER`、`FAILED`、`CANCELLED`、`RECONCILING`。这些是独立任务状态，不是现有 finish 支持的状态值。

| 恢复时观测 | 动作 |
| --- | --- |
| QUEUED | 主 Agent 按并发上限领取并下发 |
| DISPATCHING / 下发确认未知 | 先按 attempt_id 查询执行器；不能直接再开一个 Agent |
| RUNNING 且执行器仍存活 | 继续跟随原执行，不重新下发 |
| RUNNING 且失联或租约到期 | 进入 RECONCILING，核验进程、产物与外部动作；超时不等于未执行 |
| WAITING_USER | 恢复待问事项，等待并关联后续答复 |
| FAILED | 保存失败分类；明确允许重试时建新 Attempt，保留旧检查点 |
| SUCCEEDED 且回复未确认 | 查询已有投递结果，支持时按回复去重键重投；不重跑业务任务 |

高影响外部动作的检查点包含操作 ID、意图、已知结果与核验依据。崩溃可能发生在动作成功与结果保存之间；结果未知时优先核验，不能靠记忆写入幂等承诺业务动作恰好执行一次。QQ 适配器或执行器不支持查询/去重时，无法可靠判定的投递与动作保留为待核验，交由用户处理。

取消记录表示请求取消；实际执行器确认停止后才标记 CANCELLED，不把写入状态视为已停止进程。

## HTTP 与并发边界

已提供独立 `/v1/executions` 命名空间：幂等接受任务、按会话/状态有界列举、读取任务、领取、条件保存检查点、完成/失败/取消请求；另提供有界的调度上下文读取/更新。请求格式见接入指南，不要求现有 Session API 接受这些新字段。

- 复用设备 Bearer 鉴权；当前为单用户可信设备模型，不新增多用户隔离承诺。
- 接受消息时，去重键与任务映射在同一事务保存；重复投递返回原 task_id。HTTP Idempotency-Key 仍保护相同请求重试，两种去重用途分别维护。
- 状态迁移与检查点使用版本/CAS 和 attempt_id，拒绝旧执行器写入新尝试；检查点与状态同一事务提交。冲突返回当前版本，调用方核验后合并，不盲目覆盖。
- 首版可限定一个主调度器；若支持多个调度器，领取必须原子化，使用服务端时间的可续期租约与单调 fencing token。租约失效不自动授权重复执行外部动作，执行器也须拒绝旧 token。
- 持久化任务与待下发记录后再发送，回复同样使用持久 outbox。没有执行器/QQ 侧去重与查询能力时，outbox 本身不能保证恰好一次投递。

## 存储与成本

低频调度摘要和检查点可复用现有原子持久化基础，但需要新 schema、逻辑路径及验证规则；执行记录增加受管executions路径，通用put禁止更改，写入只能走专用API。

首版不保存完整提示词、聊天、工具输出或代码 diff；检查点目标≤1,200字，详情用受控产物引用。列表只返回摘要，每页最多50条。心跳只在需要租约时发生，不写成长期记忆日志。

现有 store 每次提交保存完整修订且没有 GC。若把频繁心跳/事件直接写入该 store，会放大磁盘与写入成本；实现前需测量真实任务频率和基线，决定是否将运行事件放入独立持久存储。首版先做低频快照，不为了“有记录”建立无限事件流水。当前快照是恢复依据；调试历史按明确保留策略归档，删除执行记录不删除项目知识。

## 实现顺序与验收

1. **任务与检查点（已实现）**：受管执行记录、来源去重、CAS、会话/状态查询和原子更新；用重启恢复、重复消息与旧 Attempt 写入测试验证。单主调度器也需保护下发/回传的不确定状态。
2. **QQ/Pi 接入**：确认机器人和执行器实际接口，在接受、下发、压缩/阶段边界、回传处自动保存；验证主 Agent 清空上下文后能列出多个任务并继续处理，重复下发不新建执行实例。
3. **运行保障（后续）**：按实际并发需要补租约、fencing、持久 outbox 和保留策略；模拟“保存后未下发”“已下发未确认”“动作成功未保存”“完成未回复”，检查恢复不会盲目重跑。

API 持久化测试通过与 QQ/Pi 端到端接入通过分别报告。只有入口、分发和回传均接入并验证，才可声称远程调度已具备崩溃恢复能力。
